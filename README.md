## v13 audit and implementation sequence

| Phase | Evidence from deployed v13 | Implemented change |
| --- | --- | --- |
| 1. Establish the baseline | Hatchable identified v13 as live. Its release contained 15 files and zero functions. A historical signaling route was disabled. | Archived all 15 files byte for byte and checked them against the deployment manifest. Tested the original receiver and sender together in a browser. |
| 2. Fix consent and integrity | The incoming file-start handler could create a receiver independently of an accepted offer. A transfer-complete message could display success without checking all files. Size overrun was detected after staging. | Bind each frame to the accepted offer, file order, byte limits and session. Verify actual bytes and wait for peer receipt. A modern sender waits for final batch acknowledgement. Preserve v13 compatibility in either direction. |
| 3. Bound memory and recover | Hashing called arrayBuffer on the whole file. Cleanup and receipt paths could leave staged chunks or object URLs. A disrupted receiver lost its in-memory state. | Incremental SHA-256, small send frames, adaptive buffering and verified 1 MiB checkpoints. The sender must prove it holds the saved prefix before skipping bytes. Atomic storage writes, per-file leases, quota checks and explicit cleanup protect interrupted sessions. |
| 4. Improve pairing and routing | Both peers had to exchange an offer and a reply. A local-network setting, existing public STUN option, QR image import and QR-based ICE restart were already available. | Retained offline QR, manual codes, rotating QR frames, image import and connection rescue in the new flow. Default pairing uses local routes. The optional different-networks mode uses the existing STUN providers. The browser selects a viable ICE route. Logs report route type, connection state and round-trip time when provided. Short interruptions get a grace period. |
| 5. Build temporary signaling | v13 exchanged setup data optically. An active server mailbox would introduce a new privacy boundary. | Implemented a one-scan client and a separate, disabled server package. One encrypted offer and answer, separate sender and receiver credentials, one accepted answer, three-minute access expiry and capped storage. File bytes stay on the data channel. Activation is pending. |
| 6. Simplify daily sharing | v13 exposed device roles, connection steps and diagnostics up front. Its peer to peer chat had no saved identity or clear delivery feedback. | Send, Receive and Recent Devices views. Explicit first-time code comparison and fresh signed proof on reconnect. Saved-device connections withhold sharing until verification. Tap-to-copy text, safe HTTP(S) links, confirmed message delivery between new peers, and manual clipboard fallbacks. Classic remains available. |
| 7. Validate offline upgrades | The old service worker cached arbitrary same-origin GETs and could return one cached shell across different navigation routes. | The new worker uses a release-specific list of app files, validates content and commits a readiness marker last. Separate main and Classic offline pages. Auth, signaling and private URLs stay outside the new cache. Rollback and upgrade simulations cover mixed old/new caches. |

## What passed

- The original production manifest matched every baseline file. All 25 public files on the tested project draft matched the local candidate hashes. Hatchable's deployment dry run passed with zero errors and zero warnings. The candidate had zero active server routes or migrations.
- All 38 Node tests passed, including the opt-in 250 MiB stress case. The dependency-free run used real cryptography and controlled transport/storage conditions. It covered consent, integrity, corruption, identity replay, cancellation, cleanup, mixed-version behavior, encrypted signaling and offline cache policy. The optional 250 MiB case independently verified all stored blocks and forbade any whole-file source read.
- Two peers in managed desktop Chromium 157 paired using the hosted draft, declined and reoffered a file, and downloaded 1,310,725 bytes identical to the original. Both generated QR images also paired the browsers through the actual QR photo-import controls. The real service worker installed, controlled the hosted page and cached both interfaces.
- The assembled candidate exchanged files and messages with an unmodified v13 peer in both directions in a browser fixture. The tests compared the downloaded bytes. A returning device passed a fresh identity challenge. A substituted browser was disconnected before any file or text could be shared by the pinned session.
- A storage suite passed 23 test groups, including an upgrade that retained saved blocks, cleanup under hard quota and recovery from temporary browser read failures. A 24 MiB local staging test reloaded a 7 MiB prefix and read at most 1 MiB at a time at application level. Browser internals and final Files/Downloads export may use additional space.
- A 64 MiB file crossed a real Chromium WebRTC connection and every downloaded block matched the source. A 128 MiB browser transfer hit a real storage quota despite the browser estimating over 10 GB available. Independent IndexedDB tests reproduced the failure without BeamSync. With the final patch, a 160 MiB offer reached a real storage refusal after 113 MiB. Both peers reported the cause. The receiver withheld the partial download, retained only committed blocks, released the checkpoint immediately and let the user discard it. The 250 MiB ceiling passed in the synthetic harness. Its usability on the iPad and Galaxy is unverified.
- Five integrated interruption scenarios covered a partial block, a fully saved file, ordinary receipt without retention, explicit cancel and a corrupted acknowledgement. One test exposed a race when a channel started closing before its close event. Following the fix, the receiver kept the first 1,048,576 verified bytes and downloaded the exact original file after reconnecting.
- The encrypted one-scan client established a real WebRTC channel using a simulated signaling mailbox. The handler's SQL operations were exercised on SQLite with PostgreSQL time expressions translated. Hatchable's actual signaling route, scheduler and PostgreSQL integration still require a hosted trial after authorization.
- Layout and controls were exercised at 320, 390, 820 and 1024 CSS pixels in Chromium, including keyboard focus, trust confirmation, code image import and clipboard fallbacks. These are desktop-engine results. Native iPadOS and Android behavior requires the checks below.

## Recovery and trust in practice

1. To keep a checkpoint, select **Keep verified parts** on the receiver when accepting a file. A normal disconnect keeps verified blocks. **Cancel transfer** removes staged data. Both peers need the upgraded protocol for resume.
2. Reconnect and offer the same original file. Accept it again on the same receiving browser and origin, using the same trust context. The sender rereads the file to establish identity and confirm its prefix. Only the remaining network payload needs to cross the connection. Resume operates per file. Previously completed files in a reoffered batch can be sent again.
3. Interrupted checkpoints expire after 24 hours. BeamSync cleans them the next time it accesses that browser storage. Browser eviction, private browsing or clearing site data can remove them sooner. Closing a tab in the middle of a write can require up to 45 seconds before another tab can resume. Verified downloads are tab-scoped until you save them to Files or Downloads. [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)
4. To save a device, connect, choose **Compare device codes** on both screens, compare every group, then name and trust the browser. **Reconnect** pins that saved identity during a fresh pairing. Both devices must have BeamSync open. The app has no background discovery service. File receipt still requires acceptance.

## Pending decisions and device checks

**One-scan approval.** The proposed Hatchable service would receive encrypted setup messages and see network metadata such as the two requests' IP addresses, timing and ciphertext size. Its QR contains a secret in the URL fragment. It grants its holder the chance to pair until expiry. File contents, filenames and chat messages bypass the service. The sender requests deletion after pairing, and a scheduled sweep removes expired records. This is an application access deadline, without a guarantee about physical deletion or platform log/backup retention. No recurring schedule, paid API or relay has been enabled.

**TURN.** STUN helps browsers find direct routes. Some mobile, corporate and guest networks block every usable direct route. A TURN relay would carry encrypted file traffic, see traffic metadata and consume bandwidth. No relay is configured. Failures on restricted networks should be recorded; approval and a bandwidth budget would precede any relay trial. [WebRTC TURN overview](https://webrtc.org/getting-started/turn-server)

## Rollback

The project has only staged source changes. The live v13 deployment requires no rollback today. The archive's `baseline-v13/public/` tree and `deployment-manifest.json` identify the exact working release from October 16, 2026 UTC. For a future software rollback, restore those public files, check all 15 SHA-256 values, dry-run the project, then release the restored build. Retain the new files as unused staged sources unless their removal is approved. Check both a fresh browser and a warmed Home Screen install. Neither restoration nor the test plan requires clearing user browser storage or deleting any database.

The optional server migration is additive and isolated from the v13 table. If signaling is ever activated, disable creation first and ensure the expiry cleanup runs for the last outstanding rooms when reverting. A client-only rollback cannot undo a database migration.
